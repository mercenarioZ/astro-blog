Every async API in Node ends up in the same place. `setTimeout`, `fs.readFile`, `setImmediate` and a socket's `data` event all lead to one `while` loop in C, inside a library called libuv. Most of the "event loop rules" we memorise are just the order of lines in that loop. This post follows the async APIs down to it, with one interactive diagram of the loop.

## Six lines, one order

```js
setTimeout(() => console.log("setTimeout"), 0);
setImmediate(() => console.log("setImmediate"));
Promise.resolve().then(() => console.log("promise"));
queueMicrotask(() => console.log("queueMicrotask"));
process.nextTick(() => console.log("nextTick"));
console.log("sync");
```

Run it as a CommonJS file on Node 24:

```
sync
nextTick
promise
queueMicrotask
setTimeout
setImmediate
```

It looks like a priority table. It is not. The six calls hand their callbacks to different owners, and each owner runs its queue at a different moment.

## Who owns what

| API                                             | Owner                   | When it runs                         |
| ----------------------------------------------- | ----------------------- | ------------------------------------ |
| plain code                                      | V8, the call stack      | now, to completion                   |
| `process.nextTick`                              | Node                    | after every callback                 |
| `Promise.then`, `await`, `queueMicrotask`       | V8, the microtask queue | after every callback, after nextTick |
| `setTimeout`, I/O, `setImmediate`, close events | **libuv**               | when the loop reaches their phase    |

V8 is only the engine: one call stack, no timers, no I/O, no event loop. The same V8 runs in Chrome. Node turns it into a server runtime by adding libuv, plus C++ glue between the two. So the bottom row, the real async work, is libuv's.

## libuv's while loop

```bash
node -p "process.versions.uv"
```

Mine says `1.52.1` on Node v24.22.1. libuv ships inside Node. It wraps `epoll` (Linux), `kqueue` (macOS) and IOCP (Windows) behind one API, and runs the loop. Here is `uv_run()` from `src/unix/core.c`, trimmed:

```c
r = uv__loop_alive(loop);

if (mode == UV_RUN_DEFAULT && r != 0 && loop->stop_flag == 0) {
  uv__update_time(loop);
  uv__run_timers(loop);
}

while (r != 0 && loop->stop_flag == 0) {
  uv__run_pending(loop);
  uv__run_idle(loop);
  uv__run_prepare(loop);

  timeout = 0;
  if ((mode == UV_RUN_ONCE && can_sleep) || mode == UV_RUN_DEFAULT)
    timeout = uv__backend_timeout(loop);

  uv__io_poll(loop, timeout);

  for (r = 0; r < 8 && !uv__queue_empty(&loop->pending_queue); r++)
    uv__run_pending(loop);

  uv__run_check(loop);
  uv__run_closing_handles(loop);

  uv__update_time(loop);
  uv__run_timers(loop);

  r = uv__loop_alive(loop);
}
```

That is the whole event loop. Drawn in call order:

Each async API has a fixed seat:

- **I/O callbacks** run in 3 · Poll, the only step that sleeps.
- **`setImmediate`** runs in 4 · Check.
- **Close events** run in 5 · Close.
- **Timers** run in 6 · Timers, plus one pass before the loop starts.

## Between libuv's callbacks: nextTick and promises

The strip under the diagram is not libuv. After each callback libuv calls, Node empties the `nextTick` queue, then the promise queue, and repeats until both are empty. Only then does libuv move on.

A "callback" is any time the loop calls into your JavaScript: the main script, one `setTimeout` function, one `fs.readFile` callback. Each counts separately, even inside one phase:

```js
setTimeout(() => {
  console.log("timeout 1");
  process.nextTick(() => console.log("  tick from timeout 1"));
}, 0);
setTimeout(() => {
  console.log("timeout 2");
  Promise.resolve().then(() => console.log("  promise from timeout 2"));
}, 0);
console.log("main script");
process.nextTick(() => console.log("  tick from main"));
```

```
main script
  tick from main
timeout 1
  tick from timeout 1
timeout 2
  promise from timeout 2
```

The tick squeezes in between the two timers. Node has done this since [v11.0.0](https://github.com/nodejs/node/pull/22842).

Two side effects. A `nextTick` that keeps scheduling `nextTick` starves the loop. And in an `.mjs` file, promises run before ticks (`sync, promise, queueMicrotask, nextTick, ...`), because Node evaluates ES modules asynchronously.

## setImmediate vs setTimeout(0)

**Inside an I/O callback**, `setImmediate` always wins. You are in 3 · Poll, and Check comes before Timers. Press "inside an I/O callback" on the diagram.

**From the main script**, it is a race. `setTimeout(fn, 0)` is really 1 ms, and `uv_run()` runs due timers once before the loop. If 1 ms has passed by then, the timeout wins. If not, the immediate does. Press "from the main script".

```
two calls alone         39 immediate, 1 timeout   (40 runs)
plus 2 ms busy-wait     20 timeout                (20 runs)
```

Put everything together inside an I/O callback, and the order is fixed:

```js
const fs = require("node:fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("5 timeout"), 0);
  setImmediate(() => console.log("4 immediate"));
  Promise.resolve().then(() => console.log("3 promise"));
  process.nextTick(() => console.log("2 nextTick"));
  console.log("1 sync");
});
```

## Single-threaded, so why a thread pool?

JavaScript runs on one thread. libuv does not.

Some work blocks, and the OS offers no non-blocking version of it everywhere: reading a file, `dns.lookup()`, `crypto.pbkdf2()`, zlib. Run it on the JavaScript thread and everything freezes. So libuv runs it on a pool of four helper threads (`UV_THREADPOOL_SIZE` to change), then hands the result back.

The pool runs C code, never your JavaScript. Your callbacks still run one at a time on the main thread, so they never race and never need a lock. Sockets skip the pool entirely: the kernel already handles them without blocking.

## One fs.readFile, end to end

1. **V8** runs `fs.readFile()`. Node passes it to libuv and returns at once.
2. **libuv** gives the read to a pool thread.
3. The script ends, and the loop starts.
4. **libuv** sleeps in Poll until the pool thread wakes it.
5. **Node** enters V8 and runs your callback.
6. **Node** drains ticks and promises, then back to 4.

JavaScript never waits for I/O, and the loop truly sleeps when idle. That is the whole trick. Block the main thread yourself, with a heavy loop or `readFileSync`, and it is gone.

## Why your program will not exit

The gate on the diagram is `uv__loop_alive()`:

```c
static int uv__loop_alive(const uv_loop_t* loop) {
  return uv__has_active_handles(loop) ||
         uv__has_active_reqs(loop) ||
         !uv__queue_empty(&loop->pending_queue) ||
         loop->closing_handles != NULL;
}
```

An open server or an uncleared `setInterval` keeps it true. A promise that never settles does not, because promises never reach libuv.

## And in the browser?

There is no libuv there. Chrome runs the same V8, but splits libuv's jobs across Chromium:

| Job        | Node              | Chrome                            |
| ---------- | ----------------- | --------------------------------- |
| Event loop | libuv             | renderer main thread (Blink)      |
| Timers     | libuv             | Blink tasks                       |
| Network    | libuv             | network service process           |
| Files      | libuv thread pool | browser process                   |
| Threads    | libuv thread pool | Chromium thread pool, Web Workers |

Microtasks behave the same in both. Everything libuv does is where they differ.

## What I took from it

Every Node ordering question I used to answer from memory, I can now answer by finding the seat on one `while` loop. Plain code first, microtasks after every callback, then wherever libuv happens to be standing.
